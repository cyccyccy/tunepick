**关键结论（与主理人的怀疑方向相反，需要明确指出）：**

> **"曲名对上了但歌手完全不对"的条目，几乎都不在 strict 的 63 首里，而在 relaxed 的 14 条"relaxedUpside"里。**
> 原因是 `match.js` 在**本地歌手可信**时给了歌手 0.4 权重：`(0.6t+0.4a) ≥ 0.65` 的硬门槛使得"歌手完全不对"的候选最多只能拿到 `weak`（如 entry 0：`titleSim 0.96 / artistSim 0.1 → strict 0.616 = weak`）。

> 真正的问题不是"strict 太松"，而是 **strict 里 38 首的歌手从未被任何本地证据佐证**（`[Unknown Artist]` 36 + 伪歌手 2），而报告把它们与"已佐证"的 25 首混在同一个 63% 里。

## ③ 逐问题发现

### Q2 —— `tierRelaxed` 不是 `tier` 的超集：**是设计（且是缺陷性设计），不是 bug 意义上的"更宽松"**

**代码事实**（`src/04-run-l2.js` 349–354、429–434、393–394、443–444）：
```
best = pickBest(local, pool);          // 排序键：strict 档 → strict 分 → relaxed 档 → relaxed 分
block.tier        = best.bestScore.strict.tier;
block.tierRelaxed = best.bestScore.relaxed.tier;   // ← 同一个候选的两个档位
```
即 `tierRelaxed` **不是**"把判定线放宽后重新取最优"，而是"**用 strict 排序选出的那个候选**，再读它的 relaxed 档位"。这不是 bug，但它使"relaxed = 更宽松"的直觉**不成立**。

**实测**：源级 28 处 strict/relaxed 不一致（10 处 strict 命中但 relaxed 不命中 + 18 处反之）。

**报告里所有基于 relaxed 的表述都要检查**：

| 报告处 | 原值 | 复核 |
|---|---|---|
| §4.1 网易云 relaxed 列（样本 69% / 加权 73.3%） | 69 / 73.3 | ⚠️ **低估**。用 `match.js` 自己的 `scoreCandidate`、**只把排序改成 relaxed 优先**后，网易云 relaxed 命中 = **77**（不是 69） |
| §2.3 + §1.1 "两档并集 78%（加权 84.3%）是真正的召回天花板" | 78 | ✅ **成立**。我独立验证：relaxed 优先重排后曲目级命中 = **78**，与"并集"完全一致；重排只新纳入 1 首（entry 5 的另一个候选），且该首本已在并集内 |
| §2.3 "实测有 6 首通过 strict 却掉到 relaxed 的 weak" | 6 | ⚠️ 实测 **8 首**。原因分两类：① 时长差 19–29s × 0.85 系数（5 首：#5/38/44/52/57）② 曲名相似度本身 <0.8（3 首：#53 0.773、#94 0.667、#99 0.75）。报告只讲了 ① |

**结论**：报告"不能把 relaxed 当 strict 上限"的警告是对的、且比它说的更严重（28 处反例）；"并集 78% 是天花板"的结论**成立**；但 §4.1 的 relaxed 列必须改（69→77）或明确标注"这是 strict 最优候选的 relaxed 档，不是 relaxed 最优"。

### Q3 —— 网易云软封的检测与数据可信度

**(1) `src/util/net.js` 层面并没有把"HTTP 200 + 业务错误码"判为失败。**
`webGet`/`webPost` 的 `ok = res.ok && !parseError` —— **不含任何业务错误码检查**。软封识别只写在两个调用点：`searchNetease`（查 `body.code`）与 `fetchNeteaseLyric`（查 `body.code`）。
→ 所以"坑不会复发"这句话**只对网易云搜索/歌词成立**；对 **MusicBrainz 的 `body.error` 没有任何地方检查**（这正是下面 Q6 的问题根源），对任何新接入的源也同样不设防。**必须把"业务错误体判定"下沉到 `net.js`（或统一的响应校验层）。**

**(2) 第二轮数据没有混入软封空响应 —— 已确认。**
- 187 次网易云请求：`code=200` ×187、`status=200` ×187、`via=fetch` ×187、`endpoint=cloudsearch-pc` ×187、`msg` 出现次数 **0**、`ok=false` **0** 次。
- 仅 6 次请求返回 0 候选，全部是**合理空**：4 次查询词本身就是广告串（`公众号：小草新剧社，所有内容仅供试听…`，`songCount=0`），2 次是 `4D 360° 拉据高调 朱煜凡` 这类脏查询（`songCount=0`）。
- ✅ 结论：最终 63% 建立在干净的 187 次 `code=200` 响应上。

**(3) 分段特征检查：不存在渐进式软封。**
按 sampleIndex 每 20 首分桶（我查了 `attempts[].candidateCount / songCount / elapsedMs`）：

| 桶 | 请求 | 平均候选 | 平均 songCount | 0 候选 | code≠200 | 命中率 |
|---|---|---|---|---|---|---|
| 0–19 | 58 | 7.47 | 208 | 2 | 0 | 20% |
| 20–39 | 35 | 6.63 | 199 | 4 | 0 | 60% |
| 40–59 | 44 | 7.59 | 204 | 0 | 0 | 75% |
| 60–79 | 21 | 7.24 | 246 | 0 | 0 | 90% |
| 80–99 | 29 | 7.41 | 157 | 0 | 0 | 70% |

→ 候选数与 `songCount` **无系统性衰减**，0 封禁贯穿全程。命中率的桶间差异来自分层构成（0–19 桶 100% 是 Layer A），不是源退化。
✅ **63% 既没有被软封抬高，也没有被压低。**

**(4) 但"旧端点 405"的细节无法验证（报告需删改）：**
留存证据只有 `data/l2-run.log`：`netease requests 248 / errors 0 / emptyResult 246`、summary `netease 0%`、遥测里**没有 `blocked` 字段（旧版结构）**，"`code:405`"与"`操作频繁`"在全部日志中**一次都没有出现**。
- "**程序不会报错、只会把命中率算成 0%**" ✅ 成立（`errors:0` + 命中率 0%，且旧版没有 abort 逻辑）。

### Q6 —— 被忽略的失败模式

**(1) MB 的 87 次空结果**——**不是被限速"封"，但其中至少 24 次是被限速/繁忙导致的错误响应，被代码误记为"空结果"。**

我做了 3 次实测（`qa/probe-net.js`，1.3s 间隔）：

| 探测 | via | ok | status(记录) | body |
|---|---|---|---|---|
| MB 中文冷门查询 | curl | **true** | **200** | `{"error":"The MusicBrainz web server is currently busy. Please try again later."}` |
| MB 英文知名查询 | curl | **true** | **200** | 同上（busy） |
| CAA release | curl | false | 0 | HTML 404 |

**因果链（这就是缺陷所在）**：
1. `webGet` 的 `viaCurl()` 把 `status` **硬编码为 `parseError ? 0 : 200`**，且 `ok = !parseError` → **curl 路径根本无法观测 HTTP 状态码**；
2. MB 繁忙时返回的是**能正常 JSON 解析**的 `{"error": ...}`（HTTP 200/503 都一样）；
3. `searchMusicBrainz` 只检查 `r.body.recordings`：`undefined → recs=[]`，而 `r.ok===true` ⇒ **计入 `emptyResult`，不计入 `errors`**。
→ 所以 **`telemetry.musicbrainz.errors = 0` 是假的**；MB 那 87 次"空结果"里：
- **63 次** `count === 0`（其中 43 次走 fetch、状态真实为 200）→ **是源真的没有**；
- **24 次** `count` 字段缺失（`body` 解析成功但没有 `count`）→ **全部走 curl、状态不可观测** → **极可能是上述 `{"error":"…busy…"}` 错误体**（24/87 = 27.6%）。

**对结论的影响（诚实评估）**：
- 报告"MB 只有 28%、对本曲库基本无效"的**结论不变**（若扣掉 24 次无效请求，MB 的 28% 是被**低估**而不是高估，方向上更支持该结论）。
- 但报告 §2.4 表格里"MusicBrainz 137 次请求、0 错误、0 封禁"**实质不成立**，必须改成"113 次有效请求（63 次确认 0 结果、24 次源繁忙被误记、另 50 次有结果）+ 24 次响应不可验证"。
- **这是需要回修的源码缺陷**（不是报告表述问题）：`net.js` 不检查业务错误体 + curl 路径伪造 status。同样的坑会让"源存活率"监控（报告 §9.2 建议的新指标）**永远报 100% 可用**。

**(2) CAA 是"沙箱限制"还是"源不可用"？——报告表述会误导。**
- 我实测：`https://coverartarchive.org/release/<id>` 有一次**成功抵达源站**并获得 **CAA 自己的 404 页面**（`<title>404 Not Found</title> … No cover art found for release f1e0b6e1-…`），说明该域名**并非被沙箱硬屏蔽**；另一次（另一个 release id）fetch + curl(noproxy) **双双超时 19s**。
- 结论：是**沙箱网络间歇性不可达**（同一 URL 时而通、时而超时），叠加**网络层只解析 JSON**（CAA 默认返回 HTML/图片，`net.js` 会把它判成 `parseError → ok=false, status=0`）。
- **报告不能把"沙箱限制"写成"源不可用"**：按报告现有措辞，产品会得出"MB+封面这条路走不通"的印象；而实际上"把 `Accept: application/json` 传给 CAA + 保留真实 status"在**可达环境下是可行的**。另外我抽到的 `f25432e1…`（entry 25 `寸草心/东方传奇`）在 CAA 上**确实没有封面**（这是源侧限制，与沙箱无关）——所以**M-07 靠 CAA 兜底的前景仍然很差**，报告"必须先改口径"的判断是对的。
- 与 (1) 同源：CAA 的 404/超时在 `telemetry` 里同样会以 `status: 0 / ok: false` 出现，无法区分"源没有图"和"网络不通"。

**(3) 我自己另外找到的可疑点 → 见 ⑤（共 8 条）。**

## ⑤ 我新发现的可疑点（报告未提）

**A. `net.js` 的 curl 路径伪造 HTTP 状态码 —— 影响所有源的"健康度"结论。**
`viaCurl()` 里 `status: parseError ? 0 : 200`。本次 MB 137 次请求里 **59 次走 curl**（43%），其"status 200"全是假的；网易云 187 次全是 fetch（幸未受影响）。这条 + 不检查业务错误体，一起让"0 错误、0 封禁"类结论失去证据力。

**B. `ok = res.ok || status===404` 的宽松分支。**
`webGet` 里 `if (r.ok || r.status === 404) return r;` —— 404 被当作"成功"直接返回、不再回退 curl。对 CAA 这类"用 404 表示没有图"的接口是合理的，但对"源被墙返回 404"的情形会把失败当成功。建议把"HTTP 层次的失败"与"业务层次的空"分开记录。

**C. `topCandidates` 只留 5 条，把"离线复算"的能力永久封顶。**
`rescore()` 注释已自认这一点。实测受影响面很大：网易云 **93/100** 的条目候选池 > 5 条。所以**任何"改评分规则 → 离线复算"的迭代都在被截断的池上进行**，报告 §9.3.4（修掉 64 秒差异的漏洞）之后的重算也是在这个受限池上做的。建议至少保存每查询的候选（或去重后 top-20）。

**D. 命中曲目的时长一致性是 90.5%，正好压在报告建议的 90% 线上（没有余量）。**
报告的 §9.2 想把"命中候选 |Δduration| ≤15s 的比例 ≥90%"作为新指标。我实测：63 首网易云 strict 命中里，时长差 **≤15s 的 57 首（90.5%）**、**>15s 的 6 首（9.5%）**，且 **>30s 的 0 首**（6 首全部落在 19–29s：`#5/38/44/52/57/62`）。
→ 该指标现状**刚好达成**（90.5% ≥ 90%），但只有 0.5pp 余量，样本量 63 下 1 首的波动就是 1.6pp。**建议把目标写成"≤20s 达 100%（现 100%）+ ≤15s ≥90%（现 90.5%）"两条**，并把 >15s 的命中一律降级为"待审阅"——它恰恰是最有价值的"同名不同曲"防线（§9.3.4 的 Bluebird/Blue Bird 案例）。

**E. relaxed 的 0.92/0.80 阈值是从拉丁文长度标定的，对中日韩短标题同时产生假阳和假阴。**
- 假阳：entry 70 `Better Man (Live)`/张杰 → MB 返回 `Better Man`/**Pearl Jam**（titleSim 1、artistSim 0），relaxed 判 **exact**；
- 假阴：entry 75 `一笑而过`/那英 → 网易云与 MB **都**返回 `一笑而过`/**那英**（歌手完全相同、时长差 0、简繁差异），relaxed 只给 **weak**（titleSim 0.75 < 0.8）。
→ 中文短标题的编辑距离比值天然被压缩（1 个字差 = 0.67~0.75），`0.92/0.80` 这两条线在 CJK 上不可用。建议按字符数与语种分别定标，或改用"简繁折叠后再比 + 字数归一化"。
（我为此写了一个**示意性**简繁折叠表（`qa-lib.js` 中 50 字，非 OpenCC）：折叠后 entry 99 `禁止悲傷`↔`禁止悲伤` 相似度 0.75→**1.0**，A/B 口径的假阴由 3 首降到 2 首。）

**F. MB 的边际贡献可以精确量化：+1 首，但它同时"纠错"了 18 首中的一部分。**
- 仅 MB 命中、网易云未命中：**1 首**（entry 90 `天使的翅膀/徐誉滕`）→ 边际召回 **+1pp**；
- 两源都命中但给出**不同歌手**：**18 首**。典型：entry 49 网易云=`吴雨啊`(翻唱上传者) vs MB=**周杰伦**(正确)；entry 52 网易云=`许巍` vs MB=**雷婷**（本地标题 `蓝莲花--雷婷` 的右侧就是本文件演唱者 → MB 其实更对）；entry 81 网易云=`粉白噪音` vs MB=**周杰倫**。
→ 报告"MB 对本库基本无效"从**召回**角度成立，但"双源交叉能识别出'在线歌手不唯一'这件事"价值很高（**18 首**）——这正是 M-01"歌手正确率"最便宜的置信度来源。报告完全没提这一点。另：entry 67 网易云=`Ahrix`(对) vs MB=`Howie`(错)，说明交叉也不是单向可信，必须做成"两源一致才提置信度"。

**G. §7.3 把 Layer A 的失败几乎全部归因于 `Cydian`，与数据不符。**
`Cydian` 确实是最大伪歌手（325 首 / 11.2%），但：
- 63 首命中里的 38 首"歌手未佐证"中，**36 首是 `[Unknown Artist]`**、只有 **2 首是 `Cydian`**；
- 全库 `[Unknown Artist]` **704 首（24.3%）**，是 `Cydian` 的 2.2 倍；
- Layer A 的 20 首命中 4 首，失败的主因是**装饰噪声 + 广告串**（`4D【360°】珍藏版音律`、`中【3D环绕】A Namorada`、`公众号：小草新剧社…`）。
→ 产品优先级应是：**装饰剥离 & 广告串剔除 > `[Unknown Artist]` 处理 > `Cydian` 名单**。报告的顺序（把 Cydian 放在最前）会误导排期。

**H. `al-` 只有 3 张图；`mf-` 的 2889 个 id 全部唯一但字节全同。**
这两条说明"封面覆盖"在 Navidrome 侧的真实可用信息量极低（**3 张专辑图**），报告建议"M-07 靠 L2 的 picId ≥60%"是对的，但应同时说明"L1 侧新增封面能力 ≈ 0"，避免把 L1 也算进封面指标的分母。

## ⑦ 智能路由判定

> **判定：`源码有缺陷需回修`（小范围、8 行级） + `报告表述需修正`（多处）——** 但**结论本身（"方案成立、PRD 目标必须下调"）站得住，不需要重做原型**。

**必须回修（源码，会污染未来的监控与口径）**
1. `src/util/net.js`：`viaCurl()` 不应伪造 `status: 200`；应在 `webGet/webPost` 增加**业务错误体判定**（`body.code != 200`、`body.error` 存在）并把它作为独立的失败类别返回（`businessError`），而不是让调用点各自判断。
2. `src/04-run-l2.js` → `searchMusicBrainz`：必须检查 `r.body.error`（MB 繁忙时的 `{"error":…}`），把它计入 `errors` 而不是 `emptyResult`；当前写法让"源繁忙"静默变成"源没有这首歌"。
3. `src/04-run-l2.js` → `rescore()`：不应覆盖 `telemetry`（或用独立字段保存），否则每次离线重算都会把源健康度证据清零。

**必须改表述（报告，不改会误导决策）**
- §2.3：6 首 → **8 首**；
- §2.4：删掉"连续 246 次 code:405 / 约第 50 次 / 持续 ≥25 分钟"中**无证据的部分**；把全零遥测表换成 `l2-netease.log` / `l2-run.log` 的真实值；补一句"端点轮换机制本轮未被实测覆盖（187 次全走 cloudsearch-pc）"；
- §4.1：relaxed 列（69% / 73.3%）标注为"strict 最优候选的 relaxed 档"，真值为 **77%**；
- §4.2：S3 发出次数 36 → **60**；删/改"每首 S1/S2 必发"；
- §4.4：标注 year/album 的"L1 ∪ 任一在线源"口径（否则与 §4.3 的 52 无法对账）；
- §4.5：把"歌手被证实 28"改为"**本地歌手字段可用 28 / 在线歌手与本地一致 26**"，并明确"可用 ≠ 一致"；
- §3.5：删掉"逐曲生成的渐变占位图"，改为"**2889 首返回同一张固定水印图（99809B / md5 3b696af3ef82，内容为'全网音乐排行榜'）**"；
